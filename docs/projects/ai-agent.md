## 1. 개요

AI Agent 서버는 사용자 요청을 받아 Vertex AI를 호출하고 응답을 반환하는 역할을 한다. 이 워크로드는 일반적인 웹 서비스와 두 가지 지점에서 다르게 동작한다.

- **I/O 바운드다.** 요청 대부분의 시간이 외부 API 응답 대기에 소요되며, 파드 자체의 CPU·메모리 소비는 크지 않다.
- **요청 처리 시간이 길고 편차가 크다.** 단순 질의와 장문 추론의 소요 시간 차이가 크다.

따라서 리소스 사용률을 전제로 설계된 기본 오토스케일링과, 짧은 요청 수명을 전제로 한 배포 전략을 그대로 적용할 수 없었다. 여기에 더해 3개 환경의 형상을 일관되게 유지하면서, 개발자가 인프라 담당자를 거치지 않고 배포할 수 있는 경로를 만드는 것이 요구사항이었다.

## 3. 기술 선택과 근거

### 형상 관리

| 도구 | 역할 |
|---|---|
| Helm | 클러스터 애드온 배포 및 버전 관리 |
| Kustomize | 애플리케이션 이미지 태그 및 k8s 리소스의 환경별 오버레이 |
| Terraform | GCP 리소스 프로비저닝 |

애드온과 애플리케이션의 형상 관리 도구를 분리했다. 애드온은 외부에서 배포되는 차트를 버전 단위로 고정·업그레이드하는 것이 목적이므로 Helm이 적합했고, 애플리케이션은 환경별 차이가 이미지 태그와 리소스 값 정도로 한정되어 오버레이 diff가 PR에 그대로 드러나는 Kustomize가 리뷰 관점에서 유리했다.

### 배포 파이프라인

| 단계 | 도구 | 역할 |
|---|---|---|
| CI | GitHub Actions | 이미지 빌드 및 매니페스트 태그 갱신 커밋 |
| CD | ArgoCD | Git 상태 기준 선언적 동기화, 개발자 셀프서비스 배포 |
| 배포 전략 | Argo Rollouts | 카나리 배포 및 롤백 |

배포 권한을 인프라 담당자에게 집중시키지 않고 개발자가 직접 배포할 수 있도록 ArgoCD를 경유하는 경로를 열었다. Git이 단일 진실 공급원이 되므로 배포 이력과 롤백 지점이 커밋으로 남고, 권한은 ArgoCD Project 단위로 제한된다.

> **[작성 필요]** 개발자에게 연 권한의 범위를 구체적으로 서술. 어떤 리소스까지 배포 가능한지, 프로덕션 동기화에 승인 절차를 뒀는지 — 이 부분이 플랫폼 엔지니어링 관점을 보여주는 지점.

### 오토스케일링 — KEDA

기본 HPA는 CPU·메모리 사용률을 지표로 삼는다. 그러나 Agent 서버는 외부 API 응답을 대기하는 시간이 대부분이므로, **요청이 쌓여 응답 지연이 발생하는 상황에서도 리소스 사용률은 낮게 유지된다.** 부하가 실재하는데 스케일 아웃이 트리거되지 않는 구조적 불일치가 있었다.

이에 KEDA를 도입해 **HTTP RPS를 스케일링 지표로 사용**하도록 변경했다. 유입 요청량은 동시 처리 중인 요청 수를 반영하므로, 리소스 지표보다 실제 부하에 선행하는 신호가 된다.

> **[확인 필요]** RPS 수집 방식을 명시할 것 — KEDA `http-add-on`(인터셉터 프록시) 경유인지, Prometheus scaler로 인그레스·서비스 메시 메트릭을 참조하는지. 선택 이유 한 줄이면 충분.

**남은 과제.** RPS는 동시 처리 요청 수의 대리 지표다. 요청별 처리 시간 편차가 큰 워크로드에서는 동일한 RPS에서도 실제 부하가 달라질 수 있어, in-flight 요청 수 기반 지표를 후속 검토 대상으로 두고 있다.

> **[작성 필요]** 스케일 인 시 in-flight 요청 처리. LLM 호출은 응답까지 시간이 걸리므로 축소 과정에서 파드가 종료되면 처리 중인 요청이 유실된다. `terminationGracePeriodSeconds` 조정, preStop 훅, KEDA cooldown 설정 등 실제 대응한 내용이 있다면 이 프로젝트에서 가장 강한 항목이 됨.

### 관측

Loki(로그) · Grafana(대시보드) · Tempo(분산 트레이싱)로 스택을 구성했다.

> **[작성 필요]** Agent 워크로드에 특화된 관측 지표를 명시. Vertex AI 호출 레이턴시, 토큰 사용량, 에러율·타임아웃 비율 등 무엇을 대시보드에 두고 무엇을 알람으로 걸었는지.

### 비용 최적화 (PoC 진행 중)

CAST AI를 도입해 노드 비용 최적화를 검토하고 있다. Agent 워크로드는 I/O 바운드 특성상 파드당 리소스 요청량을 상대적으로 낮게 잡을 수 있어, 노드당 파드 밀도를 높이는 방향이 유효하다고 판단했다.

> **[작성 필요]** PoC의 판단 기준. 무엇을 측정해서 도입 여부를 결정할 것인지(비용 절감률, 스팟 중단 빈도, 스케줄링 지연 등).
